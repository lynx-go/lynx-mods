# 跨模块调用面——供给方 domain 接口 + 根包导出构造器

2026-10-26 决策。notification v0.1.0 砍掉显式发送 RPC 时留下的口子：**Go internal
可见性下，应用代码与其他模块如何同步调用一个模块的写能力**。本 ADR 定通道与
形态，不排期任何功能的实现。

## 背景

- internal 布局（ADR-0004① / ADR-0006）后，模块对外的 Go 面只有两处：
  `domain/<m>`（契约：聚合、端口接口、事件常量）与 CLI 生成的桥接包
  `modules/<m>/module.go`（注入物，仅转发 `Module`/`Assemble`）。
- 现有跨模块协作两条通道，各有边界：
  - **事件目录**（契约②）：异步、fire-and-forget、无返回值——session 吊销
    联动、notification 生成通知。适合「发生了事实，谁关心谁订阅」。
  - **消费方只读适配器**（userReader 模式，三处先例：session/access/
    organization 读 identity 用户）：消费方 import 供给方 domain 端口，
    自持实现**直查**供给方表。只读、简单键值查询；写方法一律报错。
- **缺口：同步调用他模块的写能力**。真实驱动：
  1. notification 显式发送——应用代码（后台任务、启动期引导、业务流程）
     给用户发系统通知，v0.1.0 因本口子未决而砍掉（写入只剩事件订阅）；
  2. invite（organization 邀请流）——「建成员 + 发通知」的跨模块编排，
     需要步骤与结果，事件给不了；
  3. audit 显式 Record 目前只有 RPC 形态——要求运行中的服务与认证主体，
     服务启动期、后台任务、事务内的应用代码用不上。

## Considered Options

- **A. 供给方 domain 接口 + 模块根包手写导出构造器 + 应用组合根显式接线
  （选定）**：能力契约在 domain（本来就在 internal 外），实现归模块
  infra，根包 `exports.go` 纯转发构造器。编译期显式、可 mock、零新机制
  （导入改写/文件清单/三方合并全部照旧）。
- **B. kernel 服务注册表**（`Assembly` 暴露能力 map，`Deps` 注入，按名取
  实现）：运行时服务定位器，类型安全靠断言——与「编译期显式」哲学冲突
  （ADR-0005 否运行时 DI 的同款理由），kernel API 加面。
- **C. RPC 自调用**（gRPC client 环回本进程）：网络环回 + 认证主体尴尬
  （服务间身份是分布式问题，modular monolith 不该引入）+ 单进程事务
  优势作废。
- **D. 事件请求-响应**：异步语义强套同步需求，时序与结果不可控。
- **E. userReader 对称推广到写路径**（消费方自持适配器直写供给方表）：
  写逻辑复制进消费方 + 直写他人的表 = 所有权漂移——恰是 userReader
  写方法一律报错要防的事。**读写的不对称是本质的：读可消费方自持
  （表只读、语义简单），写必须供给方导出。**

## Decision

1. **通道分级判断表**（新增通道 ③，优先从上往下）：
   | 需求形态 | 通道 |
   |---|---|
   | 异步联动、事实广播 | ① 事件目录 |
   | 读他模块数据、简单键值查询 | ② 消费方 domain 端口 + 自持只读适配器 |
   | 同步调他模块写能力 / 跨模块业务步骤 | ③ **供给方 domain 能力接口 + 根包导出构造器（本 ADR）** |
   | 跨进程、外部系统触发 | ④ 模块自身 RPC 面（一直就有） |

2. **形态三件**：
   - 供给方在 `domain/<m>` 定义对外能力接口（如
     `notification.Sender`——方法签名不染驱动类型，ctx 承载事务）；
   - 模块根包新增**手写** `exports.go`（`package <m>`，与桥接包同包）：
     纯转发构造器（`func NewSender(db *bun.DB) Sender` → internal infra
     实现）。它是模块作者的稳定契约面，**参与三方合并**（update 热区
     极小——纯转发）；桥接包是注入物不参与合并，能力导出不该是注入物。
     Go internal 可见性下，模块根包是唯一能同时看到 domain 契约与
     internal 实现的层；
   - 应用组合根显式接线：`sender := notification.NewSender(db)`，传给
     需要它的应用代码或其他模块装配参数。编译期类型安全、测试可 mock
     （domain 接口对应用可见）。
3. **同事务语义**：调用方在 `uow` 事务内调能力方法，供给方仓储经
   `buntx.Conn(ctx)` 取连接——跨模块写与业务自然同事务（audit「显式
   Record 同事务」的语义由此通用化）；无事务 ctx 则独立提交。
4. **零机制新增**：`exports.go` 走既有文件清单/导入改写（internal 路径
   映射已覆盖根包文件里的 import）/三方合并/doctor 完整性——CLI 无需
   任何改动；模块仓内它照常 `go build ./...` 覆盖。

## Consequences

- notification v0.2 显式发送、invite、audit 应用内记录有了标准通道——
  各功能仍按真实需求排期，本 ADR 只定姿势。
- 模块根包出现手写 Go 文件（新形态）；v0.1.0 的 notification 暂无
  exports.go，第一个采用者是首个消费者出现时的供给方。
- 契约②措辞不变（跨模块仍只允许 import 他模块 domain——能力接口就在
  domain）；新增的只是「实现经根包构造器导出给应用组合根」。
- 源码分发的取舍不变：应用嫌转发构造器不顺手，直接改 exports.go 即可
  （源码归你），它不参与桥接式注入物的保护。
- **开放问题**：能力接口粒度（用例粒度 vs 聚合粒度）待第一个消费者
  定标；单模块多能力（≥2 接口）时 exports.go 的组织纪律届时一并定。
