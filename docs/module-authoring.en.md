# Module Authoring Guide (English)

> 中文版(源文档): [module-authoring.md](module-authoring.md) — in case of divergence, the Chinese version is canonical.

This guide serves two audiences:

- **App developers** — you installed a few registry modules and now need to write your own business domain;
- **Module contributors** — you want to publish a business domain back to this registry.

Both share the same structure and contracts; the only difference is the final
section (whether it is distributed via `lynx-start add`). A full read takes about
15 minutes; it pairs best with `modules/demo` (466 lines, the minimal complete
example) and `modules/identity` (authenticator + config section).

---

## 0. Three rules to remember first

1. **The source is yours.** Once installed, a module is your code — change
   fields, swap repositories, delete methods; nobody's permission needed, the
   compiler has your back. This guide is about "what structure to follow to
   enjoy contract protection", not "what you must do".
2. **Cross-module dependencies are domain-level only.** A cross-module import
   may only target the other module's `domain/<name>` package; app/infra/api
   cross-imports do not compile (enforced by directory layout) — the compiler
   IS the architecture guardrail.
3. **Security-sensitive implementations live in the kernel; module source holds
   only orchestration.** The line between source distribution and libraries is
   not "important vs unimportant" but **"will the app want to change it" vs
   "must a CVE be fixable remotely"**:

   | Nature of the code | Channel | Examples |
   |---|---|---|
   | Business logic users will change | module source (`lynx-start add`) | aggregates, use-case flows, policy trade-offs |
   | Users won't change it; CVEs must ship as patches | kernel (Go module, semver) | Argon2 parameters, JWT verification, timing-alignment decoy |
   | Interface derivatives | generated (buf / protoc plugins) | DTOs, HTTP/gRPC skeletons |

   Once module source is installed it is disconnected from the registry —
   `lynx-start update` is a human-triggered three-way merge, so security fixes
   cannot rely on it. Therefore any implementation where "wrong parameters are
   a vulnerability" (hash parameters, constant-time comparison, token
   verification, randomness) sinks into the kernel: the app runs
   `go get kernel@fix` and it is fixed, no per-module merging. Cautionary tale:
   identity once hard-coded the timing-alignment decoy Argon2 constant in
   module source — after the kernel bumped parameters, the decoy silently
   mismatched and timing alignment silently stopped working; since v0.1.1 it
   calls `password.DummyHash()` (lazily generated by the kernel, parameters
   always match).
4. **The six contracts** (ADR-0004) at a glance:

   | # | Contract | Where |
   |---|---|---|
   | 1 | Layer ownership | `domain/<m>` + `internal/{app,api,infra}/<m>` + `proto/<m>/v1` |
   | 2 | Cross-module domain-level DAG only | `kernel.Module.DependsOn` declaration, validated at startup |
   | 3 | Config autonomy | own Config struct + `configkit.LoadSection` |
   | 4 | Migration isolation | own goose version table `goose_<m>_db`, no cross-module foreign keys |
   | 5 | Error-code space | `errcode.MustRegister("<m>")` |
   | 6 | No tenancy preset in the kernel | multi-tenancy is a future cross-cutting module |

## 1. Module anatomy

The module structure **inside the registry repo** (contributor side) and its
**installed form** in an app (ADR-0006 install mapping — module code is
never modified):

```
modules/<m>/ (registry)         <app>/ (installed, tail segment flattened)
├── domain/<m>/                 ├── modules/<m>/
│   ├── item.go                 │   ├── module.go        # bridge (add-generated: forwards Module/Assemble)
│   ├── repo.go                 │   ├── domain/          # outward contract surface: aggregates/ports/sentinels/events
│   └── guard_test.go           │   ├── internal/app/    # use-case layer: orchestrates domain and ports
├── internal/{app,api,infra}/<m>/ │   ├── internal/api/    # Service impl (thin forwarding) + Module()/Assemble()
└── proto/<m>/v1/<m>.proto      │   ├── internal/infra/  # bun repository + migrations/ (embed.FS)
                                │   └── genproto/<m>/v1/ # relocated by lynx-start generate
                                └── proto/<m>/v1/<m>.proto  # API contract source (app-root central)
```

The dependency direction is constant: `api → app → domain ← infra`. Assembly
lives in the module's `internal/api/<m>/module.go`; the app reaches it through
the bridge package `modules/<m>` (Go internal visibility: the module's
internal/** is importable only from inside modules/<m>/).

## 2. Hands-on: write a `todo` module (private to your app)

All steps happen **in your application repository**; each step names the
corresponding demo-module file so you can copy across.

### Step 1: domain — aggregate, errors, repository port

```
domain/todo/task.go   # Task aggregate + NewTask/Complete (invariants live here)
domain/todo/repo.go   # type Repository interface { Create/Get/List/Update... }
```

Key points (cf. `modules/demo/domain/demo/item.go`):

```go
var space = errcode.MustRegister("todo")          // contract 5: space name = module name

var (
    ErrTaskNotFound = space.New("TASK_NOT_FOUND", "todo task not found")
    ErrEmptyTitle   = space.New("EMPTY_TITLE", "title must not be empty")
)

// Event catalog (contract 2): the app layer's publishes and Module().PublishedEvents share the same constants.
const (
    EventTaskCreated = "todo.task.created"
)
```

Sentinel errors are translated to `grpc/status` (carrying ErrorInfo) by the app
layer; repository interface methods always take a `context.Context` — infra
adapters pull the transactional connection from ctx (`kernel/uow/buntx`).

### Step 2: infra — bun repository + migrations

```
internal/infra/todo/repo.go                      # implements domain/todo.Repository
internal/infra/todo/migrations/00001_init.sql    # CREATE TABLE ... (goose format)
internal/infra/todo/migrations/embed.go          # //go:embed *.sql → var FS embed.FS
```

Table naming convention `<module>_<entity>`; **no cross-module foreign keys**
(contract 4). Updates use an explicit column whitelist (see
`modules/demo/internal/infra/demo/repo.go`). The migration chain runs under a
goosekit-owned version table, so a rollback never affects other modules.

### Step 3: app — use-case orchestration

```
internal/app/todo/todo.go    # type UseCase struct{repo, tx, events, now}
```

Cf. `modules/demo/internal/app/demo/demo.go`: wrap writes in
`u.tx.Run(ctx, func(ctx) error { ... })` so repositories and event publishing
share one transaction; event names reference domain constants (e.g.
`todo.EventTaskCreated`); payloads MUST be encoded with `json.Marshal`
(hand-rolled strings produce invalid JSON when values contain quotes or
backslashes); publish through the module's own publish helper (same shape in
demo/identity).

### Step 4: proto — API contract and policy declarations

```
proto/todo/v1/todo.proto
```

Cf. `modules/demo/proto/demo/v1/demo.proto`:

```proto
import "google/api/annotations.proto";
import "grpcapi/v1/policy.proto";

option (grpcapi.v1.api) = { api: "public", default_exposure: EXPOSURE_PUBLIC };

service TodoService {
  // authenticated by default (Bearer once identity is installed); public methods declare it explicitly:
  option (grpcapi.v1.service) = { default_policy: { anonymous: true } };

  rpc CreateTask(CreateTaskRequest) returns (Task) {
    option (google.api.http) = { post: "/v1/tasks" body: "*" };
  }
}
```

Policy annotation cheat sheet (full semantics in `scaffold/proto/grpcapi/v1/policy.proto`):

- `anonymous: true` — the method is public;
- `permissions: [...]` (MATCH_ALL) / `roles: [...]` (MATCH_ANY) — take effect
  once the access module is installed (compared after the Enricher injects claims);
- methods without an explicit `anonymous` declaration **require authentication
  automatically** when an authenticator is installed (fail-closed).

### Step 5: api — Service implementation + assembly

```
internal/api/todo/service.go   # thin forwarding: validation goes to protovalidate, business to the use-case layer
internal/api/todo/module.go    # Module() + Assemble()
```

The `module.go` skeleton (cf. `modules/demo/internal/api/demo/module.go`;
imports are rewritten to your app's paths at install time):

```go
func Module() kernel.Module {
    return kernel.Module{
        Name:        "todo",
        Description: "todo tasks",
        Policies:    []protoreflect.FileDescriptor{todov1.File_todo_v1_todo_proto},
        Migrations:  migrations.FS,
        PublishedEvents: []string{todo.EventTaskCreated},               // domain constants, same source as the publish sites
        ConsumedEvents: nil,                                           // declare here when subscribing to cross-module events
        // DependsOn: []string{"identity"},   // only if the domain layer imports identity's domain package
    }
}

func Assemble(deps kernel.Deps) (kernel.Assembly, error) {
    uc := apptodo.New(infratodo.NewRepository(deps.DB), deps.Tx, deps.Events)
    return kernel.Assembly{
        Registrations: []server.Registration{newRegistration(NewService(uc))},
    }, nil
}
```

**Event catalog safety net**: `ValidateModules` (runs at startup and during
migrate) cross-validates catalogs — published names are legal and
module-prefixed, no duplicate publishers; **every consumed event has an
installed publisher**. Typos in subscribed event names, upstream renames, or a
missing publisher module all fail closed at startup instead of silently never
firing at runtime. Per contract 2, consumers do not import publisher code;
consumed event-name constants are defined in the consumer's own domain (cf.
session's `IdentityUserPasswordChanged`).

For a config section (cf. identity): define a Config struct + `ApplyDefaults`
in the app layer; in Assemble call
`configkit.LoadSection(deps.Config, "todo", cfg.ApplyDefaults, &cfg)`, and add
the fragment to `configs/config.yaml` by hand (registry modules get it appended
automatically via the item.json `configFragment`).

### Step 6: generate code

```bash
mise run generate    # lynx-start generate: buf pipeline + genproto relocation into modules/<m>/genproto/
go mod tidy
```

### Step 7: register

Append (inside the anchors) to the `Installed` list in `modules/modules.go`
(`lynx-start add` injects this automatically — copy the shape for hand-written
private modules; the import points at the module bridge package):

```go
import todo "<app-module-path>/modules/todo"
// ...
{Module: todo.Module(), Assemble: todo.Assemble},
```

Then `mise run db:migrate && mise run dev`. HTTP routing, authentication
requirements and permission declarations for new methods are all driven by
proto annotations — main.go never changes: it is the stable part of the
skeleton; only modules.go moves as modules come and go.

## 3. Assembly contribution cheat sheet

| Contribution | Static (`Module()`) | Dynamic (`Assemble()`→`Assembly`) | Example |
|---|---|---|---|
| gRPC/HTTP services | — | `Registrations` | demo |
| Policy descriptors | `Policies` | — | all |
| Migration chains | `Migrations` | — | all |
| Published event catalog | `PublishedEvents` | — | demo / identity / session / access |
| Consumed event catalog | `ConsumedEvents` | — | session (password-change联动 revocation) |
| Event subscriptions / background services | — | `Services` | session |
| Scheduled tasks | — | `Tasks` | — |
| Authenticators | — | `Authenticators` | identity (Bearer) |
| Post-authn enrichment | — | `Enrichers` | access (roles/permissions claims) |
| Interceptor stages | — | `Stages` (audit=50/ratelimit=40/usage=60) | — |
| Hand-written HTTP routes | `ExtraRoutes` | `ExtraRoutes` | — |
| Dependency declarations | `DependsOn` | — | session→identity |

`Assemble` receives `kernel.Deps`: `DB` (bun), `Tx` (uow), `Events` (publisher
port), `Bus` (subscription side), `Config`, `Logger`. Dependencies are
explicit; there is no generated DI.

## 4. Publishing to the registry (module contributors)

Put the module into `modules/<name>/` of this repo as a **real Go module**:

1. Ship its own `go.mod` (module path like
   `github.com/lynx-go/lynx-start/modules/<name>`), `buf.yaml`/`buf.gen.yaml`,
   and committed genproto — compiled and tested inside this repo, so kernel
   breaking changes surface in this repo's CI instead of blowing up in some
   app at install time;
2. Write `item.json`:

   ```json
   {
     "name": "todo",
     "version": "0.1.0",
     "description": "todo tasks",
     "modulePath": "github.com/lynx-go/lynx-start/modules/todo",
     "moduleDependencies": [],
     "goDependencies": [],
     "configFragment": "todo:\n  default_page_size: 50\n",
     "publishedEvents": ["todo.task.created"]
   }
   ```

   - `moduleDependencies`: the installer validates the DAG and rewrites dependent imports from this;
   - `goDependencies`: third-party libraries the app must `go get` after install;
   - `configFragment`: the YAML fragment appended to the app's config.yaml;
   - `publishedEvents`: catalog data for display, **kept in sync with
     `Module().PublishedEvents`** (the latter is the validated source of truth);
Registering is one command (item.json skeleton / registry.json / go.work kept consistent):

   ```bash
   lynx-start registry add modules/<name>   # fill description/publishedEvents after the skeleton
   lynx-start registry check                # consistency check (CI-friendly)
   ```

3. Register `{ "name", "path" }` in the `items` of `registry/registry.json`;
4. Add to the root `go.work`; `mise run lint && mise run test` green, then commit;
5. **Releasing = pushing a git tag** `modules/<name>/v<x.y.z>` (same
   subdirectory-prefix form as `kernel/v<x.y.z>`). The tag must point at a
   commit where item.json already carries that version — the installer
   validates tag-vs-manifest consistency and rejects drift. Versioning during
   0.x: breaking changes (incompatible migrations / proto field removal or
   change / assembly signature changes) bump the minor; security fixes and
   backward-compatible additions bump the patch.

### Versioned install and update (app side)

- `lynx-start add todo@0.1.0` extracts that version's source from the tag
  (reproducible installs); without `@version` the registry worktree is taken
  (latest);
- `add` writes an **install baseline** to the user cache
  `~/.lynx-start/baselines/<appModulePath>/<name>@<commit>/` (the exact
  post-install form: rewritten imports, gofmt'd). The baseline is a rebuildable
  cache and never enters the app repo: commit only `.lynx-start/lock.json`
  (supply-chain lock) and `lynx-start.json` (manifest) — when the cache is
  missing, update/doctor rebuild it from the registry at the commit recorded
  in the lock, so cross-machine updates no longer depend on committed baselines;
- `lynx-start update todo` three-way-merges to the registry latest: **local /
  baseline / upstream**. Non-overlapping changes merge automatically; same-region
  changes get git conflict markers (`<<<<<<< yours / baseline / theirs`), the
  pre-overwrite local copy is kept in `~/.lynx-start/backups/<appModulePath>/<name>/`; files deleted
  upstream are only reported, never auto-deleted. Merging writes are not
  rollback-safe — **commit the app before update**;
- Baseline invariant: baseline ≡ the last-synced upstream form. After resolving
  conflicts the baseline stays the upstream form; your resolution survives as a
  local change that the next update naturally preserves. Old manifests (no
  `files` field) have no baseline — update will suggest `add <name> -o` to
  rebuild (this overwrites local files; commit first).

## 5. Common modification recipes (changing an installed module)

| You want | Where to change |
|---|---|
| Add a field | proto message → `mise run generate` → new migration adds the column → domain aggregate + repo whitelist column |
| Add a method | proto service + http annotation → generate → api Service implementation → app use case |
| Change config defaults | app-layer `Config.ApplyDefaults` + the matching section in the app's config.yaml |
| Subscribe to another module's events | define the consumed constant in domain + declare in `Module().ConsumedEvents` + subscribe via `deps.Bus` in Assemble (cf. session subscribing to `identity.user.password-changed`); startup validation guarantees a publisher exists |
| Tighten/loosen authentication | proto policy annotations (`anonymous` / `permissions` / `roles`) — no code changes |

After changes run `mise run lint && mise run test`. Your guard_test will catch
out-of-bounds imports (domain must not import infra/app/api).

## 6. Replacing a module's internals (customization recipes)

The code is yours — editing directly is the intended path. But different edits
co-exist with `lynx-start update`'s three-way merge at different friction
levels, from low to high:

| What you want | Recommended recipe | Update-conflict risk |
|---|---|---|
| Repository detail (one SQL / index hint) | Edit `modules/<m>/internal/infra/repo.go` in place | Low — upstream rarely touches it, and your edit has clear intent |
| Swap the whole storage implementation | Add `repo2.go` implementing the same domain port; leave the old file alone; swap the constructor in the assembly layer only | Low — new files never participate in the merge (local-only files are preserved untouched) |
| Hashing / signing / crypto parameters | **Do not edit the module** — such implementations live in kernel; bump with `go get kernel@vX` | None |
| Use-case flow / business rules | Edit `modules/<m>/internal/app` directly | Medium — the upstream's main evolution zone, but three-way merge handles "yours vs theirs" well |
| Assembly wiring (constructor args / dependency swap) | Edit Assemble in `modules/<m>/internal/api/module.go` | **High — this is the upstream hot zone**. Keep edits minimal (the one constructor line); do not refactor while you are there |

Key points:

- **New files never conflict**: merging only touches files registered in the
  install baseline; files you add (repo2.go, extra adapters) survive every
  update untouched;
- **Think before editing Assemble**: it is the seam between the module and the
  kernel, and upstream may touch it every release. If you swap an
  implementation, commit the new-implementation file and the one wiring line
  separately — on conflict you only replay the wiring;
- **The domain port is your stable anchor**: as long as the port signature
  stays, swap infra freely — contract 2 ("cross-module depends on domain
  only") protects your customization exactly as it protects modules;
- After customizing run `lynx-start doctor` (baseline/lock intact) and
  `go build ./...`.
